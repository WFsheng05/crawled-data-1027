## 二、关键坑（务必先读）

### ⚠️ 坑 1：纯 HTTP 客户端会被静默降级

| 客户端 | 结果 |
|---|---|
| Python urllib / requests | ❌ 只返回 3 条，`is_end=true` |
| Node https | ❌ 只返回 3 条 |
| **浏览器上下文 fetch** | ✅ 正常翻页 |

**现象**：`code=0` 但结果被截断，且 `cursor.is_end` 直接为 `true`。
**这比报错更坑**——你的爬虫会「优雅地」认为翻到底了。

**解法**：用 `ego_script` / `ego_js` 在 bilibili 页面上下文里 `fetch(url, {credentials:'include'})`。

### ⚠️ 坑 2：wbi 签名有额外混淆

自签 `/x/v2/reply/wbi/main` 的 `w_rid` 全部对不上页面真实值（穷举 6 种 key 组合 × 排序/清洗/编码变体均无命中）。

**解法**：用 `/x/v2/reply/main`（免签名），不用 wbi 版。

### ⚠️ 坑 3：楼中楼必须抓

| 口径 | 用户数 |
|---|---|
| 只抓一级 | 10,479 |
| 一级 + 楼中楼 | **16,485** |

**漏 6,006 个「只在楼里说话的人」**。

### ⚠️ 坑 4：Runtime.evaluate 有 15 秒硬超时

长任务不能放在一次 `evaluate` 里。**解法**：起后台任务 + 轮询 `window.__prog`。

### ⚠️ 坑 5：手写 JS MD5 容易错

算错会表现为 `-403`，容易误判成风控。**用 Python 的 hashlib**。

## 三、抓取阶段

### 3.1 接口清单

| 用途 | 接口 |
|---|---|
| BV → aid | `GET /x/web-interface/view?bvid=BVxxx` |
| 匿名 Cookie | `GET /x/frontend/finger/spi` → `data.b_3` / `data.b_4` |
| **主评论（游标）** | `GET /x/v2/reply/main?type=1&oid=<aid>&mode=2&ps=30&pagination_str={"offset":"..."}` |
| **楼中楼** | `GET /x/v2/reply/reply?type=1&oid=<aid>&root=<rpid>&pn=1&ps=20` |

- `mode=2` 热度 / `mode=3` 时间
- 必带：`User-Agent`、`Referer: https://www.bilibili.com/video/<BV>/`
- 建议带：`Cookie: buvid3=...`、`Origin`

### 3.2 实测性能

| 项目 | 数值 |
|---|---|
| 主评论页大小 | `ps=30`（ps=49 无效，会被压回 30） |
| 单页耗时 | 约 183ms |
| 3,692 页耗时 | **11 分钟** |
| 楼中楼并发 | 12 并发，19,964 条 / 53 秒 |

### 3.3 翻页逻辑

```javascript
let offset = '';
while (true) {
  const url = `https://api.bilibili.com/x/v2/reply/main?type=1&oid=${AID}`
    + `&next=0&mode=2&plat=1&ps=30`
    + `&pagination_str=${encodeURIComponent(JSON.stringify({offset}))}`;
  const j = await fetch(url, {credentials:'include'}).then(r=>r.json());
  // j.data.replies / j.data.top_replies
  // j.data.cursor.pagination_reply.next_offset   ← 下一页游标
  // j.data.cursor.is_end                          ← 是否到底
  const pr = (j.data.cursor||{}).pagination_reply || {};
  if (!pr.next_offset || j.data.cursor.is_end) break;
  offset = pr.next_offset;
  await new Promise(r=>setTimeout(r,25));
}
```

### 3.4 风控应对

- 单页间隔 25~400ms
- 命中 `-412`（风控）/ `-509`（限流）/ `-799` → 退避 2s→5s→11s
- 楼中楼按需抓（只抓 `rcount > 0` 的根评论）

### 4.1.1 双口径强制并报（v1.1 新增）

> 背景：外部复核指出"人头"和"声量"是两个世界——同一批数据，人头口径批评:支持 = 10.6:1，声量口径放大到 22:1。**只报一个口径会误导。**

**规则**：立场结论必须同时给出两张表：

| 口径 | 批评者 | 支持者 | 中立 |
|---|---|---|---|
| 按独立用户（一人一票） | x% | x% | x% |
| 按评论条数（原始声量） | x% | x% | x% |

并补充三个结构指标：
- **基尼系数**（发帖集中度，本样本 0.823）
- **中位数发帖数** / 只发 1 条的用户占比
- **批评者内部分层**：只发 1 条（同情基数）/ ≥10 条（活跃核心）/ ≥100 条（刷屏号）各自的人数与声量占比

### 4.2 刷屏识别

```
按 mid 分组 COUNT(*) → 降序
>100 条 → 刷屏号（2026-10-27 样本：261 个 = 1.6%，贡献 55.8%）
```

**注意**：>100 条账号**不剔除、不合并**，全部计入「冲官方」（用户指定口径）。

### 4.3 立场判定（核心）

### 4.2.1 组织化行为物证扫描（v1.1 新增）

> 背景：外部复核从本仓库数据里挖出两条硬物证，下次抓取时主动扫，不要等别人发现。

| 物证 | 检测规则 | 本样本数值 |
|---|---|---|
| **随机后缀规避折叠** | 文案尾部 `[a-z]{6,}` 乱码 / 零宽字符占比 | 6,134 条"银灰剧本"中 1,118 条带乱码 |
| **复制指令** | 含"复制我这个""加上乱码""从别的评论区搬" | 366 条 |
| **预制 Q&A 同文簇** | 同一长文案 ≥50 个不同 mid 发布 | 108 条同文 + 86 条变体 |
| **框架竞争** | 同一历史事件词（银灰）被双方引用 | 提到银灰 1,651 人分裂三股 |

**输出**：`org_evidence.md`，单独成文，作为"组织化节奏"的直接证据链。

### 4.3 立场判定（核心）

#### 四类标签

| 标签 | 定义 |
|---|---|
| **冲官方** | 批评/嘲讽/质疑官方或游戏内容 |
| **支持官方** | 为设计辩护 / 反对加强 / 否定冲的正当性 / 复读「银灰节奏复刻」 |
| **中立** | 有发言但无立场（剧情/玩梗/许愿/纯表情/排期抱怨） |
| **无实质** | 纯表情、纯数字、极短无法判断 |

#### 冲官方的子类

```
直接诉求    加强/削弱/重做/改机制/回调/优化
强度批评    打不过XX/法穿缺失/被单杀/不如XX
机制批评    启动慢/绑配队/抢条/技能敷衍
设计批评    断手/立绘/小人/模型/敷衍/压稿
剧情批评    人设/塑造/编剧/吃书
反讽        太有面子了/哪里弱了/够强了/还要什么自行车
间接暗示    只提「陪跑」「借过」「留了一手」「又是本源近卫」
冲锋话术    孝子/洗地/强度区/捂嘴/青蒜
组织行动    修墙/砌墙/填工单/救救塔露拉
直接辱骂    鹰角不当人/神人公司
```

#### 支持官方的子类

```
为设计辩护      断臂很帅 / 别的厂商不会这样做
反对加强诉求    够用了 / 没必要加强 / 强度没问题
否定冲的正当性  还没实装别急 / 别带节奏 / 游戏而已
复读银灰复刻    又是一个银灰 / 百万银灰厨复刻   ← 归支持官方！
嘲讽冲动方      百万塔厨 / 评论区一堆僵尸 / 饭圈打榜
```

#### ⚠️ 中立判定要点

**以下一律判中立**：

- **排期抱怨**：「好痛苦，一定要隔一周才开活动吗」← 用户明确要求
- 纯剧情考据、纯玩梗、纯表情、纯许愿、纯宣群、纯提问、夸PV画面
- 断手梗的**列举/接龙/提问**（「杨过」「手咋断的」）→ 中立
- 断手梗**带修复诉求**（「把手还回来」）→ 冲官方

### 4.4 规则判定的局限（重要）

**规则会系统性低估冲官方人数**：

| 阶段 | 冲官方 | 说明 |
|---|---|---|
| 初版规则 | 7,347 | 只识别明显表达 |
| 补术语 | 7,604 | 加强度黑话 |
| **8 批子代理重判** | **8,132** | **最终值** |

**原因**：
1. 反讽识别不了（「哪里弱了」被当成肯定）
2. 圈内黑话不认识（「超大上」「借过」）
3. 间接暗示抓不到（只提「陪跑」没提「加强」）

**结论：必须用子代理逐条重判。**

## 五、子代理重判流程（关键步骤）

### 5.1 分批

```bash
$PY -X utf8 mkrejudge.py
```

把「中立」用户按 8 批切分，每批约 960 条，输出到 `rejudge/r1.txt` ~ `r8.txt`

格式：`mid\t该用户全部发言(合并,截断300字)`

### 5.2 开子代理

**必须 8 个并行**，每个子代理处理一批。

**子代理 prompt 模板**：

```
你是中文评论语义判定专家。任务：判定 B 站《明日方舟》评论区中，用户对「官方/游戏」的立场。

## 输入文件
C:\total workspace\Deepseek harness\one\bili_crawl\rejudge\rN.txt
格式：每行 `mid\t该用户的全部发言(合并)`（约 960 行）

## 背景
这是针对官方「塔露拉」角色强度/设计不满的节奏。

## 判定标准
### A = 冲官方
[列出子类...]

### B = 支持官方
[列出子类...]

### C = 无立场
**关键：以下一律判 C**
- **排期抱怨**：「好痛苦一定要隔一周才开活动吗」← 明确算中立
- 纯剧情/纯玩梗/纯表情/纯许愿/纯提问/夸PV
- 断手梗列举/接龙/提问 → C；带修复诉求 → A

## 判断原则
1. 反讽必须识别：「哪里弱了」是反讽 → A
2. 拿不准时判 C（保守，不夸大）
3. 【v1.1 新增】"等实装""别急""还没上线"类话术：若上下文是劝阻批评 → B；若是敷衍护主反讽 → A。拿不准 → C 并在理由里标"边界"

## 输出
写入：...\rejudge\vN.tsv
格式：每行 `mid\tA或B或C\t理由(10字内)`
必须覆盖全部 N 行。
```

### 5.2.1 信度抽样（v1.1 新增，必做）

> 背景：外部复核指出"8 个子代理各判一批、无重叠，无法测量一致性（缺 Cohen's κ）"。下次必须补上。

**做法**：
1. 从全部中立用户中随机抽 **200 个 mid**，混入每一批（每批 25 个重复样本）
2. 8 个子代理照常判定
3. 合并后对重复样本计算 **两两 Cohen's κ** 与多数票一致率
4. κ < 0.6 的批次 → 该批全部重判（换 prompt 细化边界规则）
5. 把 κ 值写进 README 的方法论一节

**脚本**：`cohens_kappa.py`（待写，输入 vN.tsv 即可）

### 5.3 校验（必做）

```bash
$PY -X utf8 verify_all.py
```

检查每批：
- 输入行数 == 输出行数
- mid 无重复、无缺失、无错位
- 标签只有 A/B/C
- 格式 3 列

**2026-10-27 实测**：8 批 7,689 行，全部校验通过。

### 5.3.1 数据血缘规则（v1.1 新增，重要）

> 背景：外部复核发现 `official_supporters.csv`、`silver_repetition.csv` 等**中间文件存在标签污染**（混入冲塔复读、与最终表矛盾的 mid）。最终表 `stance_rejudge.csv` 是干净的。

**规则（写死，不可违反）：**

1. **`stance_rejudge.csv`（最终立场表）是唯一权威口径**，README/视频/结论只引用它
2. 中间文件（official_*、silver_repetition、hidden_neg 等）**仅供过程追溯，禁止直接引用数字**
3. 任何中间文件若要对外发布，必须先跑**交叉一致性检查**：
   ```bash
   $PY -X utf8 cross_check.py <中间文件.csv> stance_rejudge.csv
   ```
   输出：与最终表矛盾的 mid 数量 + 样例。矛盾率 > 5% 的文件不得发布
4. 发布仓库时，README 需注明"中间文件未做交叉校验，以最终表为准"

## 十二、方法论备忘

### 「最严」与「最宽」的定义

**这里的「最严」指判定标准最严苛——要求一条不漏**，而不是收紧范围。

- **最严（可核实）**：8,132 人（逐条判定）
- **最宽（含外推）**：约 8,870 人（中立中 10% 抽样仍可能是冲官方）

### 未识别 ≠ 满意

**7,342 个「中立」不等于「支持官方」。**

抽样 50 条人工判断，发现约 5 条（10%）实为冲官方。
**报告数字是下限，不是真值。**

### 反讽是最大难点

「哪里弱了」「够强了」「还要什么自行车」「太有面子了」——字面肯定，语境否定。

**只有逐条人工/子代理判定才能识别。**

### 「等实装」类话术的双向陷阱（v1.1，来自外部复核）

同一句"还没实装别急下结论"：
- 批评者说 = "别拿等实装搪塞，现在就要改" → **A 冲官方**
- 护主者说 = "别带节奏，等上线再说" → **B 支持官方**

**必须看上下文，规则层无法处理，交给子代理逐条判。**

### 沉默螺旋 vs 选择性发声（v1.1）

本样本中连"只发一条"的最温和群体，批评:支持也是 10.9:1。
**结论：不是 Noelle-Neumann 式的沉默螺旋（支持者被压制不敢说话），而是选择性发声 + 真实倾向不对称同时存在。** 下次分析时不要简单归因为"沉默的大多数挺官方"。

### 平台排序机制制造两个评论区（v1.1）

- 时间序（mode=2/3 抓取）→ 看到动员化的声量战
- 热度序（点赞排序）→ 看到理性讨论层（高赞前 10 无复读）
- **报告时必须说明抓的是哪个排序**，本仓库默认 mode=2 时间序全量
